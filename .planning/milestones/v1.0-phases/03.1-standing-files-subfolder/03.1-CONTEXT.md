<decisions>
## Implementation Decisions

### Subfolder naming & structure
- Subfolder name: `donna/` (visible, not hidden)
- Rationale: users should be able to browse and edit their own data in Obsidian or other UIs — hidden folders work against that
- All standing files go in `donna/`: role.md, recurring.md, role-research.md, config.md
- Future standing files (tools.md, people.md from Phase 4+) also go in `donna/`
- Repo root structure after migration: `daily/` + `donna/` — user owns the root for their own notes

### Migration strategy
- Use the existing installer migration system (cumulative version-based migrations from Phase 1)
- Migration moves role.md, recurring.md, role-research.md, config.md from repo root into `donna/`
- If no standing files exist at root (fresh install or set-role not run yet): create `donna/` folder, skip file moves
- No workflow-level fallback — installer migration is the single mechanism
- `donna/` path is a fixed convention, not configurable — no new config fields needed

### Scope of path updates
- All workflow references change from `<storage_repo>/role.md` to `<storage_repo>/donna/role.md` (inline convention, same pattern as before)
- Affected workflows: set-role.md, begin-the-day.md, setup.md, done.md (if it references standing files)
- setup.md updated for new users: creates `donna/` and places config.md there instead of repo root
- No shared variable or constant — inline `donna/` path in each reference, keeping it grep-able

### Claude's Discretion
- Migration implementation details (git mv vs file move + commit)
- Whether to update the installer's file structure creation to include donna/
- Test coverage for migration edge cases
- Order of operations in the migration script

</decisions>
