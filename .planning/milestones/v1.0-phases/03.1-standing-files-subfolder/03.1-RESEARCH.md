## Summary

Phase 03.1 is a pure refactoring phase: no new capabilities are added, only storage layout is improved. The work divides into three parts: (1) a new migration script that moves standing files from repo root into `donna/`, (2) search-and-replace path updates across four workflow files, and (3) updating `setup.md` so new installs create `donna/` instead of writing standing files to repo root.

The migration system is already well-established (`migrations/001-initial.cjs` as the template, `src/migrator.cjs` as the runner). The next migration will be `002-standing-files-subfolder.cjs`. The migrator's `up()` contract — receiving `{ donnaDir, fs, path, os }` — operates on `~/.donna/`, NOT on the user's storage repo. Standing file migration therefore happens inside the workflow at runtime (not in `migrator.cjs`), because the migrator has no knowledge of the user's storage repo path.

**Primary recommendation:** The "migration" for standing files is a workflow-level operation: a new step in `setup.md` (or a separate migration workflow) detects files at repo root and moves them to `donna/`. The installer migration (`002-...cjs`) only needs to update any `~/.donna/`-scoped state, if any exists — it does not touch the storage repo.

## Architecture Patterns

### Migration System Deep Dive

The migrator in `src/migrator.cjs` has this contract:

```javascript
// migrations/NNN-name.cjs
module.exports = {
    version: "0.x.y",          // informational only
    description: "Human-readable changelog line",
    up(ctx) {
        // ctx = { donnaDir, fs, path, os }
        // donnaDir = ~/.donna/   <-- NOT the storage repo
        // This function is synchronous
    },
};
```

Migration files are sorted numerically. The migrator compares file prefix integer vs `lastMigration` stored in `~/.donna/version.md`. Migrations are cumulative: a user jumping from v0.1 to v0.3 runs all intermediate migrations in order.

**Critical constraint:** `up(ctx)` only knows about `~/.donna/`. It has no mechanism to read `~/.config/donna/config.md` or resolve the storage repo path. Standing file moves (in the storage repo) CANNOT happen inside a migration file — they must happen at workflow runtime.

### The Real Migration Is in the Setup/Workflow Layer

The correct mechanism for moving `role.md`, `recurring.md`, `role-research.md`, `config.md` from repo root to `donna/`:

1. A new migration file `002-standing-files-subfolder.cjs` — creates nothing in `~/.donna/` (nothing to do there for this phase) OR is skipped entirely since there's no `~/.donna/` state to migrate.
2. The actual file move happens as a step in the affected workflows when they first run after upgrade. Each workflow detects the old path, moves the file, and continues.

**Better alternative (simpler):** Add a one-time migration step to `setup.md` (or a shared helper step called by all affected skills) that:
- Checks if `<storage_repo>/role.md` exists at root
- If yes, moves the standing files to `<storage_repo>/donna/`
- This runs opportunistically the first time any skill runs post-upgrade

**Simplest alternative (user-initiated):** The installer print output tells users to run `/donna:setup` after upgrade. `setup.md` has a migration step that moves files.

The CONTEXT.md decision says "Use the existing installer migration system" — the planner should understand that this means adding a `migrations/002-*.cjs` entry, but also that the actual file moves must occur in workflow context where the storage repo path is available.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| File existence check before move | Custom bash logic | `test -f <path>` via Bash | Already established pattern in set-role.md |
| Cumulative migrations | New migration runner | `src/migrator.cjs` already handles it | Tested, versioned, handles skip-version upgrades |
| File moves in Node.js | Manual copy+delete | `fs.renameSync()` or `fs.cpSync()` + `fs.unlinkSync()` | Built-in, atomic on same filesystem |

## Common Pitfalls

### Pitfall 1: Migrating in the Wrong Layer
**What goes wrong:** Writing the file-move logic inside `migrations/002-*.cjs` and trying to read `~/.config/donna/config.md` from within `up(ctx)`.
**Why it happens:** Conflating "installer migration" (touches `~/.donna/`) with "storage repo migration" (touches the user's git repo).
**How to avoid:** Keep `migrations/002-*.cjs` scope-limited to `ctx.donnaDir`. The storage repo file moves belong in workflow context (where `storage_repo` is known).
**Warning signs:** Any code inside `up(ctx)` that reads from `~/.config/` or touches paths outside `ctx.donnaDir`.

### Pitfall 2: Missing the `donna/` Directory Creation
**What goes wrong:** Workflows update paths to `donna/filename.md` but `donna/` doesn't exist in existing repos, causing write failures.
**Why it happens:** Only new installs get `donna/` from updated `setup.md`; existing repos need it created during migration.
**How to avoid:** The workflow-level migration step (wherever it lives) must `mkdir -p <storage_repo>/donna` before moving files.

### Pitfall 3: Forgetting the `config.md` in the Repo
**What goes wrong:** Assuming `config.md` = `~/.config/donna/config.md` and not moving the in-repo `config.md`.
**Why it happens:** Two files named `config.md` exist — one at `~/.config/donna/config.md` (bootstrap, stays put) and one at `<storage_repo>/config.md` (in-repo config, moves to `donna/`).
**How to avoid:** The CONTEXT.md explicitly lists `config.md` as moving. Treat any reference to `<storage_repo>/config.md` as a path that needs updating.
**Note:** After reading setup.md carefully, `setup.md` does NOT write `<storage_repo>/config.md`. The in-repo `config.md` is written by `set-role.md`'s save-role step. Verify all usages of `<storage_repo>/config.md` before updating.

### Pitfall 4: Partial Migration (some files moved, some not)
**What goes wrong:** Migration step fails partway through, leaving some files in root and some in `donna/`, breaking all skills.
**Why it happens:** No atomicity in file operations across multiple moves.
**How to avoid:** Move all files in a single Bash block with error handling. Check existence of each file before moving (idempotency). Log what was moved.

### Pitfall 5: Breaking the Test for `lastMigration`
**What goes wrong:** The installer test at line 95 (`assert.equal(ver.lastMigration, 1)`) fails after adding migration 002 because `lastMigration` becomes 2.
**Why it happens:** Hardcoded expected value in `test/installer.test.cjs`.
**How to avoid:** Update the test assertion to match the new expected `lastMigration` value (2) when adding the new migration.

### Migration File Template (002)
```javascript
// migrations/002-standing-files-subfolder.cjs
"use strict";

module.exports = {
    version: "0.4.0",  // set to actual release version
    description: "Standing files moved to donna/ subfolder in storage repo",
    up(ctx) {
        // Nothing to do in ~/.donna/ for this migration.
        // The actual file moves in the storage repo happen at workflow runtime
        // because the storage repo path is not available in migration context.
    },
};
```

### Bash File Move Pattern (for workflow)
```bash
# Check and move standing files from repo root to donna/ subfolder
STORAGE_REPO="<storage_repo>"
DONNA_DIR="$STORAGE_REPO/donna"
mkdir -p "$DONNA_DIR"

for FILE in role.md recurring.md role-research.md config.md; do
    if [ -f "$STORAGE_REPO/$FILE" ] && [ ! -f "$DONNA_DIR/$FILE" ]; then
        mv "$STORAGE_REPO/$FILE" "$DONNA_DIR/$FILE"
    fi
done
```

### Workflow Path Update Pattern
Before:

```
<storage_repo>/role-research.md
```

After:
```
<storage_repo>/donna/role.md
<storage_repo>/donna/recurring.md
<storage_repo>/donna/role-research.md
```

## Open Questions

1. **Where exactly does the storage-repo file migration run?**
   - What we know: Installer migration (`migrations/002-*.cjs`) cannot access the storage repo. Some workflow must do it.
   - What's unclear: Should it live in `setup.md`, in every affected workflow as a guard step, or as a standalone one-time migration skill?
   - Recommendation: Add a single "migrate-paths" step to `setup.md` (already the "configuration" skill) that runs when it detects old-style paths. This is the most discoverable place. Alternatively, add a guard step to `set-role.md` and `begin-the-day.md` that moves files opportunistically before reading them.

2. **Does `<storage_repo>/config.md` actually exist in the wild?**
   - What we know: `setup.md` does NOT write an in-repo `config.md`. Only `~/.config/donna/config.md` is written by setup.
   - What's unclear: Whether `config.md` was ever written to the storage repo by any other workflow in phases 1-3.
   - Recommendation: Search the codebase for any workflow step that writes `<storage_repo>/config.md` before assuming it needs to be moved. CONTEXT.md lists it as moving, so it likely exists or is planned.

3. **Migration 002 version number**
   - What we know: Current package version is `0.3.2`.
   - What's unclear: What version bump this phase will produce.
   - Recommendation: Use a placeholder in migration `version` field; update to actual release version when bumping.
